# Joint CMC Action Tracker — V2.0 Design

Date: 2026-09-16 (revised after review)
Status: Draft for user review
Extends `2026-09-06-joint-cmc-tracker-design.md` (v1).
Program: GS098 (GenSci × Yarrow).

## 1. Scope decision

v1 shipped the full original spec and is in daily use. After reviewing the
candidate V2.0 themes, three were chosen. V2.0 is exactly these:

1. **Bilingual** — the UI and item text readable in English and 中文.
2. **Audit log for admins** — one straightforward place to see who changed
   what, when, with filters and export.
3. **Period report export** — one click to get the monthly or quarterly
   reference pack (workbook + printable page).

Everything else considered (notifications and email, optimistic locking,
attachments, meetings, bulk edit, saved views, full-text search, SSO,
backups, multi-program) moves to the V2.x backlog in §8. V2.0 adds no
background processes, no email, and no new external services: it stays a
single container that a v1 `.env` still boots.

## 2. What v1 has that V2.0 builds on

| Area | Today | Reused in V2.0 |
|---|---|---|
| Audit trail | `audit_event` records every write with `changes` `{field: {old, new}}` and an English `summary`. `GET /activity` filters by org, actor, entity type, since. Dashboard shows the last 20 with "load more". Item detail has a History tab. | The table and query are the foundation of the Audit log page; V2.0 adds filters, labels, and export. |
| Export | `GET /export/excel` builds the original `Action Item` workbook, honouring the items filters. Admin › Export page and an Export button on the Items table. | The period report reuses the workbook builder for its item sheets. |
| Translation | The "Translation in Mandarin" column is kept only inside `provenance` JSON on imported rows. | Back-filled into real fields by a migration. |
| Dashboard | Counts, needs-attention lists, breakdowns for "now". | The report computes the same figures for a past date by replaying the audit trail. |
| Frontend | All labels are literal English strings; dates via `Intl` with the browser locale. | Strings move into `en` and `zh-CN` bundles. |

## 3. Bilingual

### 3.1 UI language

- **Library:** `react-i18next` + `i18next`. Bundles at
  `frontend/src/locales/en.json` and `zh-CN.json`, split by feature
  namespace (`common`, `items`, `board`, `dashboard`, `admin`, `auth`,
  `reports`, `audit`).
- **Choice:** topbar toggle `EN / 中文`. Persisted on the user
  (`user.locale`, `PATCH /auth/me {locale}`) so it follows the person across
  browsers, with the browser language as the first-visit default and
  `DEFAULT_LOCALE` (`en`) as the fallback. The login and accept-invite pages
  read the browser language (no user yet).
- **Coverage:** every label, button, placeholder, toast, empty state,
  validation message, status / priority / owner / kind label, column header,
  and admin screen. Dates, numbers, and relative times already use `Intl`;
  they receive the active locale instead of `undefined`.
- **Audit summaries:** the stored English `summary` is no longer rendered.
  The client builds the line from `action` + `changes` with translated field
  and value labels, so the History tab and the Audit log read correctly in
  both languages. `summary` stays in the database for the export and for
  API consumers.
- **Vocabulary terms:** `vocab_term.label_zh` (nullable). Admin › Vocabularies
  gets a second column; pickers, table cells, board cards, and reports show
  the label for the active locale, falling back to `value`. `value` stays the
  stored key so items, filters, and imports are unaffected.
- **Enforcement:** an ESLint rule (`i18next/no-literal-string`, JSX text and
  common attributes only) keeps new screens from regressing. Tests query by
  role and by the `en` bundle's strings, so the existing suite keeps working.

### 3.2 Item text

- **Fields:** `action_item.title_zh` (≤ 500) and `details_zh` (text), both
  nullable. English `title` remains required; the Chinese pair is optional.
- **Detail sheet:** a "Translation" section under the English fields, shown
  expanded when the viewer's locale is `zh-CN` or the fields are filled,
  collapsed otherwise. Both pairs are editable by any member and audited as
  ordinary field changes.
- **Table and board:** the title cell shows the title for the viewer's
  locale with the other language as a muted second line when present
  (column chooser can hide it). Sorting by title uses the displayed
  language.
- **Search:** `q` matches `title_zh` and `details_zh` in addition to the v1
  fields.
- **Import:** the "Translation in Mandarin" column populates `title_zh`
  (first line) and `details_zh` (remaining lines) with the same split rule
  as the English column. Migration `0002` back-fills the two fields from
  `provenance` for every imported row, so the existing 57 items get their
  translations without re-importing.
- **Export:** the workbook restores the `Translation in Mandarin` column
  after `Action Item`, in the original sheet order, so the file round-trips.

## 4. Audit log for admins

### 4.1 Page

New admin tab **Admin › Audit log** (`/admin/audit`), admin only. One dense
table, newest first, 50 per page, with a sticky filter bar:

| Filter | Control |
|---|---|
| Period | presets Today / 7 days / 30 days / This month / Last month / This quarter / custom from–to |
| Actor | user picker (active and deactivated) |
| Org | GenSci / Yarrow |
| What | entity type: items, updates, users, invitations, vocabulary, imports, sign-ins |
| Action | created / updated / deleted / restored / status changed / update posted / … |
| Item | entry number (`#42`) — every event on that item and its updates |
| Text | matches the summary and any changed value |

Columns: time (absolute, with relative on hover), actor + org badge, entity
(`#42 Title…` for items and updates, name for users, term for vocab, file
name for imports) as a link, action, and a one-line change summary. Any row
expands to a per-field diff table (old → new) with translated field and
value labels, the same component the History tab uses.

Filters are URL-synced so a view like "everything Yarrow changed last
month" can be bookmarked or shared between admins.

### 4.2 Data and API

- `GET /activity` gains `until`, `action`, `entity_id`, `q`, and
  `include_security` parameters; `program_id` stays implicit.
- `AuditEventOut` gains `entity_label` (resolved server-side in one query per
  page: item entry number + title, user name, vocab value, import file
  name) so the table needs no follow-up requests.
- New audit actions `signed_in`, `sign_in_failed` (email only, never the
  password), and `signed_out` on entity type `user`, written by the auth
  service. They are excluded from the dashboard feed and from the default
  audit view and shown when the "sign-ins" filter is on.
- Index `audit_event(actor_id, occurred_at)` and `audit_event(action)`.
- Audit rows stay append-only: no API deletes or edits them. The admin
  "Users" page gets a "View activity" shortcut per user that opens the audit
  log pre-filtered.

### 4.3 Export

**Export** button on the Audit log applies the current filters and returns
`GET /activity/export` → `audit-log-<from>-<to>.xlsx`, one row per event:

`Time`, `Actor`, `Org`, `Entity type`, `Entity`, `Action`, `Field`,
`Old value`, `New value`, `Summary`. Events with several changed fields
produce one row per field so the sheet filters cleanly in Excel. Values are
rendered with the labels of the exporting admin's locale. Capped at 50 000
rows with a warning banner beyond that (narrow the period).

## 5. Period report export

### 5.1 Entry point

A top-level sidebar entry **Reports** (`/reports`), available to every user
(members write the monthly reports too). The page has:

- **Period chips:** This month, Last month, This quarter, Last quarter,
  custom from–to. Default: last month.
- **Scope:** all items, or filtered by group, owner org, category (same
  controls as the items filter bar, fewer of them).
- **Language:** follows the UI locale; a switch allows the other one so a
  Chinese-speaking user can produce the English pack for Yarrow.
- **Preview** of the summary figures and the section counts, updated as the
  period changes, so the user sees what the file will contain before
  downloading.
- **Two buttons:** *Download workbook* and *Open printable*. Both are plain
  GET links, so they can be bookmarked; the Admin › Export page links here
  for "monthly / quarterly reports".

### 5.2 Content

`GET /reports/period?from=&to=&group[]=&owner_org[]=&category[]=&lang=`
returns the report as JSON (used by the preview and the printable page);
`GET /reports/period.xlsx` with the same parameters returns the workbook.

| Sheet / section | Rows | Notes |
|---|---|---|
| **Summary** | headline figures | open at period start, open at period end, raised, completed, cancelled, reopened, overdue at end, P1 open at end, updates posted, active people per org; plus open-by-status and open-by-group at end, and per-owner-org raised / completed. |
| **Raised** | items with `raised_on` in period | original workbook columns, plus `Raised by` |
| **Completed** | items whose status changed to `completed` in period | plus `Completed on`, `Days open` (completed − raised) |
| **Status changes** | every `status_changed` event in period | item, from, to, by, when |
| **Updates** | every `item_update` with `occurred_on` in period | item, date, author, org, body |
| **Overdue at period end** | open at end with `due_on` before `to` | days overdue, assignee, last update date |
| **Open at period end** | full snapshot as of `to` | original workbook layout; this is the "where we stood" sheet |
| **Change log** | audit events in period on items and updates | same layout as §4.3 |

The Summary sheet is also the content of the printable page: a clean
one-page HTML view with the headline tiles, the two breakdown tables, and
the Raised / Completed / Overdue lists, styled for `@media print` so the
browser's "Save as PDF" produces a report attachment without a PDF library.

### 5.3 Computing "as of" a past date

The dashboard only knows "now". The report needs the state at `from` and at
`to`. V2.0 reconstructs it from the audit trail rather than adding a
snapshot table:

- `status_as_of(item, events, day)` = the `new` value of the last
  `status_changed` event on or before `day`; if none, the `old` value of the
  first `status_changed` event after `day`; if the item has never changed
  status, its current status. Items created after `day` (by `created_at`,
  or `raised_on` for imported rows) are excluded. Deleted items count until
  their `deleted` event; restores re-include them.
- `due_as_of` uses the same rule over `due_on` changes.
- Open / overdue / P1 counts at `from` and `to` follow from those two
  functions with the v1 definitions (open = action and not completed or
  cancelled).

All of this lives in one `services/reports.py`, unit-tested against a
scripted history (create → change status twice → delete → restore) so the
numbers are provably right. The rule set is documented in the printable
page's footer so report readers know how the figures were derived.

### 5.4 Reuse

The item sheets are produced by the v1 exporter's row builder with an
optional list of extra columns, so the layout the teams know is identical
across the item export, the audit export, and the report. Anything the
report needs from items goes through the existing `ItemFilters`.

## 6. Data model, API, and configuration changes

All schema changes are additive and land in migration `0002`.

| Table | Change |
|---|---|
| `user` | + `locale` (`en` \| `zh-CN`, nullable) |
| `action_item` | + `title_zh` (str 500, nullable), + `details_zh` (text, nullable); back-fill from `provenance` |
| `vocab_term` | + `label_zh` (str 200, nullable) |
| `audit_event` | + actions `signed_in`, `sign_in_failed`, `signed_out`; indexes `(actor_id, occurred_at)`, `(action)` |

| Method & path | Purpose | Role |
|---|---|---|
| PATCH `/auth/me` | set `locale` | any |
| PATCH `/items/{id}` | accepts `title_zh`, `details_zh` | any |
| PATCH `/vocab/{id}` | accepts `label_zh` | admin |
| GET `/activity` | + `until`, `action`, `entity_id`, `q`, `include_security`; returns `entity_label` | any (security rows: admin) |
| GET `/activity/export` | xlsx of filtered events | admin |
| GET `/reports/period` | JSON report | any |
| GET `/reports/period.xlsx` | workbook | any |

| Variable | Default | Purpose |
|---|---|---|
| `DEFAULT_LOCALE` | `en` | fallback UI language |
| `AUDIT_EXPORT_ROW_LIMIT` | `50000` | cap for the audit export |

Frontend additions: `i18next` + `react-i18next`, `eslint-plugin-i18next`;
routes `/admin/audit`, `/reports`, `/reports/print`; components
`AuditTable`, `AuditFilterBar`, `ChangeDiff` (shared with the History tab),
`PeriodPicker`, `ReportPreview`, `ReportPrintPage`. The OpenAPI TypeScript
client is regenerated once per phase.

## 7. Phasing

Each phase is shippable and gets its own implementation plan under
`docs/superpowers/plans/`.

1. **Audit log (2.0-alpha.1)** — backend filters, `entity_label`, sign-in
   events, indexes, export endpoint; Admin › Audit log page with URL-synced
   filters and expandable diffs; the shared `ChangeDiff` component replaces
   the History tab's renderer. Smallest phase; delivers the admin request
   first.
2. **Period reports (2.0-alpha.2)** — `services/reports.py` with the as-of
   reconstruction and its scripted-history tests; JSON and xlsx endpoints;
   Reports page with period chips, preview, printable page; exporter
   refactor for extra columns.
3. **Bilingual (2.0-beta.1)** — migration `0002` fields and back-fill;
   `label_zh` in vocab admin; i18n scaffolding and the `en` bundle extracted
   from current strings; `zh-CN` bundle; locale toggle and persistence;
   client-side audit summaries; item translation section and columns;
   import/export of the translation column; report and audit export in
   the chosen language.
4. **Release 2.0** — Playwright paths for the audit log, a report download,
   and the locale switch; frontend coverage gate at 70%; `DEPLOYMENT.md` and
   README updates; Chinese review pass on the `zh-CN` bundle by a GenSci
   user before tagging.

Bilingual is last because it touches every screen; landing it after the two
new pages means those pages are built with i18n from the start of their
own phase rather than retrofitted, and the audit summaries need the
client-side renderer that phase 1 introduces.

## 8. V2.x backlog (not in V2.0)

Considered and deferred, in the order they would be picked up:

- **Notifications and email** (invite / reset by email, assignment and due
  alerts, weekly digest). Needs SMTP config and a jobs loop.
- **Optimistic locking** on item edits with a conflict banner.
- **Attachments** stored on the data volume.
- **Bulk edit** and **saved views**.
- **Meetings** (agenda from open items, meeting mode, minutes).
- **Full-text search** over updates.
- **SSO (OIDC)**, scheduled backups, database-backed rate limiting.
- **Trend charts** from nightly snapshots (the report's as-of functions make
  a back-fill possible).
- **Multi-program UI** and the Sheet2 document checklist.

## 9. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Translation quality of the `zh-CN` bundle | Bundle reviewed by a GenSci user before the 2.0 tag; strings are keyed, so fixes are one-line edits without code changes. |
| Audit summaries rendered client-side drift from the stored English | Renderer tested against the same fixtures that produce `summary`; export still uses stored `summary` as a cross-check column. |
| As-of reconstruction is wrong for edge cases (delete / restore, imports) | Scripted-history unit tests; the printable page states the rules; the "Open at period end" sheet lists the items so a reader can spot-check. |
| Audit export too large | Row cap with a banner; period filter required for export. |
| i18n retrofit breaks existing frontend tests | Tests query by role and by `en` strings; the ESLint rule prevents new literals; phase 3 is done screen by screen with the suite green after each. |
| Migration back-fill on real data | `0002` is additive; the back-fill parses `provenance` defensively and leaves nulls where the column was `NA` or empty; the entrypoint takes a SQLite copy before `alembic upgrade`. |

## 10. Acceptance for V2.0

- A GenSci user switches the UI to 中文, sees translated labels, Chinese
  vocab labels, and the Mandarin title on every imported item; the choice
  survives logout and a different browser.
- An admin opens Admin › Audit log, filters to "Yarrow, last month, items",
  expands a row to see old → new values, and downloads the same filter as
  an Excel file; sign-ins appear only when that filter is on.
- Any user opens Reports, picks "Last quarter", reads the preview, and
  downloads a workbook with the Summary, Raised, Completed, Status changes,
  Updates, Overdue at period end, Open at period end, and Change log sheets;
  the printable page saves to PDF from the browser.
- "Open at period end" for a past date equals what the dashboard showed on
  that date (verified on the scripted history and spot-checked on GS098).
- The v1 Excel export still round-trips through import, now including the
  translation column.
- Backend coverage ≥ 80%, frontend ≥ 70%, Playwright suite green, `docker
  compose pull && docker compose up -d` from a v1 volume keeps all data.
