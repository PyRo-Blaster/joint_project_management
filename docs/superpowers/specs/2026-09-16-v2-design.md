# Joint CMC Action Tracker — V2.0 Design

Date: 2026-09-16
Status: Draft for user review
Supersedes nothing; extends `2026-09-06-joint-cmc-tracker-design.md` (v1).
Program: GS098 (GenSci × Yarrow), with groundwork for further programs.

## 1. Where v1 stands

v1 shipped everything in the original spec: accounts, audited items, timeline
updates, table + Kanban, dashboard, Excel import/export, one-image Docker
deployment with optional PostgreSQL and HTTPS. It is in real use (issue #4 was
raised by a user three days after release). Backend: 105 tests, 92% coverage.
Frontend: 36 tests, one Playwright golden path.

What v1 deliberately left out, plus what reading the code shows, is the raw
material for V2.0:

| Gap | Where it shows today |
|---|---|
| No email | Admin copies invite / reset links by hand. No reminders of any kind. |
| No notifications | Nobody learns an item was assigned to them, changed, or went overdue unless they open the dashboard. |
| No attachments | `file_path` is a free-text pointer into a shared drive. |
| Last-write-wins edits | `PATCH /items/{id}` has no version check. Two people from two orgs editing the same item silently overwrite each other. |
| Search is shallow | `q` is an `ILIKE` on title / details / notes_risks only. Updates and history are not searched. |
| One item at a time | No multi-select or bulk status / assignee / due-date changes. |
| Mandarin is hidden | Translation lives only in import `provenance`. GenSci users get an English-only UI and English-only fields. |
| Meetings are implicit | `source` stores "Meeting <d1> to <d2>" as a string. No agenda, no minutes, no "what changed since last meeting". |
| Single program | Data model has `program`, UI does not. A second program means a second container. |
| Single process | Login rate limiter is in-memory; expired sessions are never pruned; scheduler-less. |
| Dashboard is a snapshot | Counts only. No trend, aging, or cycle-time view. |
| Board ordering fixed | Cards order by priority then due date; no manual ordering. |
| Sheet2 document checklist | Not modelled. |
| Frontend coverage not gated | e2e covers one path; admin and import flows are untested end to end. |

## 2. Goals for V2.0

1. **People find out** — the app tells you what needs your attention instead
   of waiting for you to look (email + in-app notifications, digests).
2. **Two orgs can work on the same item safely** — optimistic locking, watchers,
   @mentions, attachments.
3. **Meetings become first-class** — the joint CMC meeting is where items are
   raised and closed; the app should prepare the agenda and capture outcomes.
4. **Both teams read it in their own language** — bilingual UI and optional
   bilingual title/details.
5. **Power-user throughput** — bulk edit, saved views, deep search, keyboard
   quick-switcher.
6. **Operate it for years** — SSO, backups, multi-worker safety, upgrade
   testing, reporting.

Non-goals for V2.0 (see §9 for V2.x): multi-program UI, Sheet2 document
checklist, public API tokens, mobile app, Gantt / dependency scheduling.

## 3. Feature design

### 3.1 Notifications and email

**Email transport.** New settings: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`,
`SMTP_PASSWORD`, `SMTP_STARTTLS`, `MAIL_FROM`, `MAIL_ENABLED` (default false so
v1 installs keep working). One `services/mail.py` with a `send(to, subject,
text, html)` function and a `ConsoleMailer` for dev/tests. Templates are
Jinja2 files under `app/templates/mail/`, plain text + HTML.

**When mail is enabled**, invitation and reset links are emailed directly and
the admin UI shows "sent to x@y" instead of the copyable URL (URL stays
available under a "show link" toggle for fallback).

**In-app notifications.** New table `notification` (`user_id`, `kind`,
`entity_type`, `entity_id`, `title`, `body`, `link`, `created_at`, `read_at`,
`emailed_at`). A bell in the topbar shows unread count (polled every 60 s via
`GET /notifications?unread=1`), a panel lists them, `POST
/notifications/read` marks read.

**Events that notify** (per-user preference, default on):

| Event | Recipients |
|---|---|
| Assigned to you | assignee |
| Item you watch changed (status, due, priority, assignee) | watchers minus actor |
| Update posted on an item you watch | watchers minus actor |
| You were @mentioned in an update | mentioned user |
| Item became overdue | assignee + watchers |
| Item due in `DUE_SOON_DAYS` | assignee |
| Weekly digest (per org) | every active user who opted in |

**Preferences.** `notification_preference` (`user_id`, `kind`, `in_app`,
`email`) editable on a new "Profile" page. Digest day/time is a program-level
setting (`DIGEST_WEEKDAY`, `DIGEST_HOUR_UTC`).

**Delivery.** Notifications are created synchronously inside the same service
transaction as the audit event (a `notify.py` service that listens to
`record_event`). Email sending and digests run in a lightweight scheduler:
`app/jobs/` with a `job_run` table for idempotency and one `python -m app.cli
jobs run` loop started by the entrypoint as a second process (supervised in
the same container; no Celery, no Redis). Jobs: `send_pending_mail` (every
minute), `due_scan` (daily), `weekly_digest`, `prune_sessions` (daily),
`backup_sqlite` (daily, see §3.6).

### 3.2 Collaboration on an item

**Optimistic locking.** `action_item.version` (int, +1 on every write).
`PATCH /items/{id}` accepts `If-Match: <version>` (or `version` in the body);
mismatch returns `409 conflict` with the current item in `data`. The frontend
shows a "This item changed while you were editing" banner with a diff of the
conflicting fields and a "reload / overwrite" choice. Board drag sends the
version it rendered with; on conflict it refetches and retries once.

**Watchers.** `item_watcher` (`item_id`, `user_id`, `created_at`). Auto-watch:
creator, assignee, anyone who posts an update or is mentioned. Explicit
watch/unwatch button on the detail sheet. `GET /items?watching=me`.

**@mentions.** Update bodies support `@name` completed from active users.
Stored as plain text with `@[User Name](user:12)` markers; rendered as user
chips; each mention creates a notification.

**Attachments.** `attachment` (`item_id`, `update_id` nullable, `filename`,
`content_type`, `size_bytes`, `sha256`, `storage_key`, `uploaded_by`,
`created_at`, `deleted_at`). Files stored under `/data/uploads/<sha256[:2]>/
<sha256>` on the existing volume; `MAX_UPLOAD_MB` (default 25);
allow-list of content types (pdf, office, images, csv, txt, zip).
Endpoints: `POST /items/{id}/attachments` (multipart), `GET
/attachments/{id}` (streams with `Content-Disposition`), `DELETE` (soft,
author or admin). Backup docs updated to include `/data/uploads`.
`file_path` stays as a legacy "external link" field.

**My work.** A "My work" page: items assigned to me, items I watch, items I
raised, each grouped by due state. Topbar link with the count of my overdue +
due-soon items.

**Item links.** `item_link` (`from_item_id`, `to_item_id`, `kind` ∈
`blocks` | `relates_to` | `duplicates`). Shown as chips on the detail sheet;
"blocked" status gets a "blocked by #n" hint. No scheduling logic.

### 3.3 Meetings

A joint CMC meeting is the unit of work for both teams. V2.0 models it
explicitly without turning the app into a calendar.

**Model.** `meeting` (`program_id`, `title`, `starts_on`, `ends_on`,
`status` ∈ `planned` | `held`, `minutes` text, `created_by`, `held_by`),
`meeting_item` (`meeting_id`, `item_id`, `sort_order`, `outcome` text).
`action_item.source` becomes derived: items created inside a meeting get
`source_meeting_id` (FK, nullable) and the old string stays for imported rows.

**Flows.**

- **Prepare agenda.** Create a meeting; the agenda auto-suggests: overdue,
  due before `ends_on`, blocked, and items changed since the previous held
  meeting. Add / remove / reorder items (drag).
- **During the meeting.** A focused "meeting mode" view walks the agenda:
  each row has inline status / due / assignee editing, an outcome box, a
  "raise new item" button that pre-fills `raised_on` and `source_meeting_id`,
  and a "record note" button for decisions (`kind = note`).
- **Close.** Mark held; minutes are auto-drafted from outcomes and edits made
  during the meeting (from audit events with `occurred_at` in the meeting
  window), then editable.
- **Export.** `GET /meetings/{id}/export` → xlsx with Agenda and Minutes
  sheets, and a printable HTML page (browser print to PDF; no PDF library).

**Review since.** `GET /activity?since_meeting={id}` plus a "Since last
meeting" preset on the dashboard and items filter bar.

### 3.4 Bilingual

- **UI language.** `react-i18next` with `en` and `zh-CN` bundles. Per-user
  `locale` stored on `user` (default from browser). All labels, statuses,
  priorities, and toasts translated. Dates/numbers via `Intl` with the locale.
- **Item fields.** `title_zh` and `details_zh` (nullable) alongside the
  English fields; detail sheet shows both with a "show translation" toggle;
  table shows the field in the viewer's locale with a fallback to the other.
  Import: the existing "Translation in Mandarin" column populates `title_zh`
  (first line) and `details_zh` (rest). Export: translation column restored.
- **Search** covers both language fields.

### 3.5 Throughput: bulk edit, saved views, search, quick-switcher

- **Bulk edit.** Row checkboxes in the table; a floating action bar offers
  status, priority, assignee, due date, group, category, watch, delete.
  `POST /items/bulk` `{ids, patch, version_map}`; all-or-nothing; one audit
  event per item plus one `bulk` parent event so the feed shows "changed 12
  items". Conflicts (§3.2) abort the batch with the offending ids.
- **Saved views.** `saved_view` (`program_id`, `owner_id`, `name`, `query`
  JSON, `view` ∈ `table` | `board`, `is_shared`). Sidebar section "Views";
  admins can pin org-wide views ("GenSci open P1", "Yarrow overdue"). URL
  sync stays the source of truth; a view is just a stored URL.
- **Search.** Move `q` to a single `services/search.py` that searches title,
  details, notes_risks, `*_zh`, update bodies, and attachment filenames.
  SQLite: FTS5 virtual table kept in sync by service writes; PostgreSQL:
  `tsvector` column + GIN index. Both behind one `search_ids(db, program_id,
  q)` function so the item query stays engine-neutral. Result snippets shown
  in the table's "match" column when `q` is set.
- **Quick-switcher.** `Ctrl/Cmd+K`: type `#42` to jump, or text to search;
  also lists pages and saved views.
- **Board ordering.** `action_item.board_rank` (nullable string, fractional
  ranking) set by drag within a column; default order stays priority + due
  when unset. `include_board_rank` on `PATCH`.

### 3.6 Operations and security

- **SSO.** OIDC login (`OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`,
  `OIDC_ALLOWED_DOMAINS`) via `authlib`. Users are still invite-only: an OIDC
  login matches an existing active user by email; unknown emails are refused
  with a clear message. Password login remains for accounts without SSO.
  `user.auth_provider` ∈ `password` | `oidc`, `external_id`.
- **Self-service password reset** by email when mail is enabled (`POST
  /auth/forgot-password`, same token flow as reset links, rate limited).
- **Multi-worker safety.** Rate limiter moves to a `login_attempt` table
  (pruned by the jobs loop) so `uvicorn --workers N` and PostgreSQL scale-out
  are safe. Sessions pruned daily.
- **Backups.** `python -m app.cli backup` writes a consistent SQLite copy
  (`sqlite3 .backup` API) plus a tarball of `/data/uploads` to
  `/data/backups/<timestamp>/`, keeps `BACKUP_KEEP_DAYS` (default 14); the
  daily job runs it. For PostgreSQL the command documents `pg_dump` instead.
  `python -m app.cli restore <dir>` for the SQLite case. Admin page "Backups"
  lists them and offers download.
- **Audit export.** `GET /activity/export` → xlsx of the full audit trail
  with filters; admin only.
- **Observability.** Structured JSON logs with request id and user id;
  `GET /api/health` adds jobs-loop heartbeat and last backup time; optional
  `SENTRY_DSN`.
- **Upgrade path.** CI job boots the last released v1 image with a seeded
  database, then the candidate image against the same volume, and asserts
  migrations apply and items / updates / users survive. Alembic migrations
  0002…000N are additive; no destructive change in V2.0.

### 3.7 Reporting

- **Trends.** A nightly `program_snapshot` row (date, open by status, overdue,
  due soon, P1 open, per-org counts) written by the jobs loop; the dashboard
  gains a 12-week trend chart (open vs closed, overdue) and an aging table
  (open items bucketed 0–14 / 15–30 / 31–60 / 60+ days). Historic rows are
  back-filled once from the audit trail at first run.
- **Cycle time.** Derived from `status_changed` audit events: median days from
  `open` → `completed` per group and per owner org, last 90 days.
- **Status report.** `GET /reports/status?since=` renders a printable page:
  headline numbers, closed since, new since, overdue list, per-org tables.
  Also the weekly digest body.
- **Export.** Excel export gains sheets `Updates` (one row per update) and
  `History` (audit events for the exported items), in addition to the v1
  `Action Item` sheet, so nothing is lost when someone works offline.

## 4. Data model changes (all additive)

| Table | Change |
|---|---|
| `action_item` | + `version` int default 1, + `title_zh`, `details_zh`, + `source_meeting_id` FK nullable, + `board_rank` str nullable |
| `user` | + `locale`, `timezone`, `auth_provider`, `external_id`, `last_notified_at` |
| `notification` | new |
| `notification_preference` | new |
| `item_watcher` | new (unique `item_id, user_id`) |
| `attachment` | new |
| `item_link` | new (unique `from, to, kind`) |
| `meeting`, `meeting_item` | new |
| `saved_view` | new |
| `job_run` | new |
| `login_attempt` | new (replaces in-memory limiter) |
| `program_snapshot` | new (unique `program_id, snapshot_date`) |
| `search_index` | SQLite FTS5 virtual table; PostgreSQL `tsvector` column on `action_item` + `item_update` |
| `audit_event.entity_type` | + `meeting`, `attachment`, `saved_view`, `bulk`, `notification` |
| `audit_event.action` | + `watched`, `unwatched`, `mentioned`, `attached`, `detached`, `linked`, `unlinked`, `held`, `bulk_updated`, `backed_up` |

Engine neutrality holds: JSON columns, no arrays, no partial indexes; the
only engine-specific piece is the search backend, isolated in one module.

## 5. API additions

| Method & path | Purpose | Role |
|---|---|---|
| GET `/notifications`, POST `/notifications/read`, GET/PUT `/me/preferences` | in-app notifications and preferences | any |
| PATCH `/items/{id}` with `If-Match` | optimistic locking (409 on mismatch) | any |
| POST `/items/bulk` | bulk patch | any |
| POST/DELETE `/items/{id}/watch`, GET `/items/{id}/watchers` | watchers | any |
| POST `/items/{id}/attachments`, GET/DELETE `/attachments/{id}` | files | any / author+admin |
| POST/DELETE `/items/{id}/links` | item links | any |
| GET/POST `/meetings`, GET/PATCH `/meetings/{id}`, POST `/meetings/{id}/items`, PATCH `/meetings/{id}/items/{item_id}`, POST `/meetings/{id}/hold`, GET `/meetings/{id}/export` | meetings | any (hold: admin or creator) |
| GET/POST/PATCH/DELETE `/views` | saved views | any (shared: admin) |
| GET `/search?q=` | cross-entity search for the quick-switcher | any |
| GET `/reports/status`, GET `/reports/trends` | reporting | any |
| GET `/activity/export` | audit xlsx | admin |
| POST `/auth/forgot-password`, GET `/auth/oidc/login`, GET `/auth/oidc/callback` | self-service reset, SSO | public |
| GET `/admin/backups`, POST `/admin/backups`, GET `/admin/backups/{id}` | backups | admin |
| GET `/admin/jobs` | job runs and heartbeat | admin |

All keep the v1 envelope, `X-Requested-With` rule, and cookie auth. The
generated TypeScript client is regenerated once per phase.

## 6. Frontend changes

- New routes: `/my-work`, `/meetings`, `/meetings/:id`, `/meetings/:id/live`,
  `/reports`, `/profile`, `/admin/backups`, `/admin/jobs`.
- Topbar: notification bell, quick-switcher, language toggle.
- Sidebar: "Views" section (saved views), "Meetings", "Reports".
- Table: checkbox column + bulk action bar; translated-title column; match
  snippet when searching.
- Detail sheet: watch button, attachments tab, links section, translation
  toggle, conflict banner.
- Board: manual ordering within a column (persisted), conflict retry.
- Charts for trends via a small dependency-free SVG chart component (no chart
  library) following the `dataviz` guidance: one accent, semantic status
  colours, dark-mode aware.
- Frontend coverage gate at 70% (Vitest `--coverage`), rising to 80% by V2.1.
- Playwright: add admin invite/import/export paths, meeting mode, conflict
  banner, bulk edit, and notification bell.

## 8. Phasing

Each phase is shippable on its own and gets its own implementation plan under
`docs/superpowers/plans/`.

1. **Foundations (2.0-alpha.1)** — `version` + optimistic locking with
   conflict UI; jobs loop + `job_run`; DB-backed rate limiter and session
   pruning; backups CLI + job; upgrade-path CI job; structured logs. Nothing
   user-visible beyond the conflict banner, but every later phase depends on
   it.
2. **Notify (2.0-alpha.2)** — mail transport, invite/reset by email,
   forgot-password, in-app notifications + bell, watchers, @mentions,
   preferences, due scan, weekly digest, "My work" page.
3. **Collaborate (2.0-beta.1)** — attachments, item links, bulk edit, saved
   views, FTS search, quick-switcher, board manual ordering.
4. **Meet (2.0-beta.2)** — meetings model, agenda, meeting mode, minutes,
   export, "since last meeting" filters.
5. **Speak both languages + report (2.0-rc.1)** — i18n, `*_zh` fields,
   import/export of the translation column, snapshots, trends, aging, cycle
   time, status report, Excel `Updates`/`History` sheets, audit export.
6. **Release 2.0** — OIDC SSO, admin backups/jobs pages, docs (`DEPLOYMENT.md`
   for mail/SSO/backups/uploads), e2e expansion, coverage gates, tagged image.

Estimated size relative to v1: phases 1–3 together are about one v1 phase
each; 4 and 5 are each about 1.5 v1 phases.

## 9. Deferred to V2.x

- **Multi-program UI** — program switcher, per-program membership, program
  admin. The data model already scopes everything by `program_id`; until
  then a second program is a second container. Planned for 2.1.
- **Sheet2 document checklist** — a `deliverable` entity with document
  status per stage. 2.1 or 2.2, after the meeting model proves out.
- **API tokens** for integrations (e.g. pushing items from a LIMS or Teams).
- **Recurring items / dependencies with scheduling** (Gantt).
- **Mobile-first layout** beyond responsive tweaks.

## 10. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Email misconfiguration silently drops invites | `MAIL_ENABLED` off by default; admin "send test email" button; link fallback always visible on demand |
| Jobs loop dies unnoticed | health endpoint reports heartbeat age; compose healthcheck fails after 10 min without one |
| FTS drift between SQLite and PostgreSQL | shared test suite runs the search tests on both engines in CI |
| Uploads fill the volume | size limit, allow-list, health reports free disk, backups exclude nothing but are pruned |
| i18n regressions in existing tests | `en` bundle is the current literal strings; tests query by role/label; a lint rule flags untranslated JSX text |
| Meeting model over-fits GS098 habits | keep `meeting` minimal (agenda + outcomes + minutes) and let items stay the unit of truth |
| Data loss on upgrade | additive migrations only; upgrade-path CI job; backup runs before `alembic upgrade` in the entrypoint |

## 11. Acceptance for V2.0

- A member is assigned an item and receives an email and a bell notification
  within one minute; the weekly digest arrives on the configured day.
- Two users editing the same item concurrently: the second save shows the
  conflict banner and no field is lost silently.
- An admin prepares a meeting agenda from overdue + due-soon items, runs
  meeting mode, records two outcomes and one new item, holds the meeting,
  and exports minutes; the audit trail shows every change against the actor.
- A GenSci user switches the UI to 中文 and sees translated labels and the
  Mandarin title on imported items.
- Bulk-changing 10 items' due date produces one feed entry and 10 item
  history entries; searching a word that appears only in an update finds the
  item.
- `docker compose pull && docker compose up -d` from a v1 volume completes
  with a backup taken first and all v1 data intact.
- Backend coverage ≥ 80%, frontend ≥ 70%, Playwright suite green, upgrade job
  green.
